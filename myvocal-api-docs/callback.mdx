<sub>**AI Cover** · Workflow: [AI Cover quickstart](/guides/cover-quickstart)</sub>

This callback protocol applies only to the AI Cover flows that take a `callbackUrl`:

| `webhookType` | Started by |
|---|---|
| `TRAIN_COVER_SPEAKER` | [Create a Cover voice](/api-reference/voice/addCoverVoice) |
| `EDIT_COVER_SPEAKER` | [Improve a Cover voice](/api-reference/voice/editCoverVoice) |
| `COVER_SONG` | [Generate a cover](/api-reference/cover/cover) |

These requests take longer to process, so the result is delivered asynchronously to the callback URL you
provide in the request.

<Note>
Other products do not use this protocol:

- **Speech to Text — Batch:** poll the transcription. The optional completion notification has its own
  signed (HMAC) contract; see [STT completion notifications](/guides/stt-batch-quickstart#completion-notifications).
- **Speech to Text — Real-time:** results arrive as WebSocket events on the session's socket. They are not
  HTTP callbacks; see the [real-time quickstart](/guides/stt-realtime-quickstart).
- **Text to Music and Interpretation:** poll-based; no callback (see below).
- **Text to Speech, TTS voices and account information:** the result is in the HTTP response.
</Note>

### Request
<p>Please provide a callback URL and ensure that the callback URL provided is consistent across different scenarios.</p>

<p>Please make sure that the url you provide is accessible to the public network and that the request type is <b>POST</b>.</p>

<p>If the callback URL varies, there may be inconsistencies between the callback URL used during the callback and the callback URL you provided at the time of the request.</p>

### Response
When an asynchronous request is sent successfully, we will immediately provide a webhookId. When a callback is made, this webhookId will also be included in the callback URL. You can use the webhookId to associate the request with the callback.

<ResponseField name="webhookId" type="string">
  When the request is successfully sent, a webhookId will be synchronously returned. The same information will also be called back in the callbackUrl, which is used to correlate the request and the response.
</ResponseField>

<ResponseField name="webhookType" type="string" >
<div><b>TRAIN_COVER_SPEAKER</b>: Add an AI Cover Voice</div>

<div><b>EDIT_COVER_SPEAKER</b>: Improve an AI Cover Voice</div>
<div><b>COVER_SONG</b>: Create an AI Cover song</div>

</ResponseField>

<ResponseField name="status" type="string" >
The status of this request
<div><b>SUCCESS</b>: this request is success</div>
<div><b>FAILURE</b>: this request is fail</div>


</ResponseField>


<ResponseField name="summary" type="string">
  Human-readable result summary.
</ResponseField>

<ResponseField name="data" type="Object" >
  business data
</ResponseField>

## Text-to-Music and Interpretation

The callback and `webhookId` mechanism on this page applies to the AI Cover flows listed above (`TRAIN_COVER_SPEAKER`, `EDIT_COVER_SPEAKER`, `COVER_SONG`).

**Text-to-Music and Interpretation do not use callbacks and never call your webhook.** They are poll-based: create the project, then poll the project/job endpoints until the resource reaches a terminal state. Neither product takes a callback URL parameter, and neither returns a `webhookId`.

If you are integrating Text-to-Music or Interpretation, implement polling instead — see [Async jobs, polling and retries](/guides/async-jobs-and-retries).
